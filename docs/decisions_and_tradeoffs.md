# Decisions and trade-offs

| # | Decision | Why | Trade-off / what we gave up |
|---|---|---|---|
| 1 | **Problem framing: supply readiness at the pilot-to-production hand-off**, anchored on OEM-specified EV/auto tapes | Altura vets products well at pilot. What fails is the *ramp plan*, which is built on pilot assumptions: pilot yields and pilot-qualified, often single-source materials. For OEM-specified tapes, missing SOP can forfeit a 5-7 year platform, which is a larger exposure than delayed revenue. | Narrower than "NPI excellence". Technical/commercial gating is out of scope; we take a launch that already passed G3 as the starting point. |
| 2 | **Evaluate historical launches "as of G3"** (features computed from what was known at the scale-up decision) | Prevents label leakage. The model answers the real question: "at G3, should we have known?" | Needs dated PPAP/qualification history (hence SCD2 on the source list). Fewer features are available than with hindsight. |
| 3 | **Temporal holdout** (train 2020-24, test 2025-26) instead of a random split | Mirrors deployment: score next year's launches with last year's model. Random splits overstate accuracy. | Smaller test set (107 launches), so metrics are noisier. |
| 4 | **Champion chosen automatically by holdout AUC** (gradient boosting vs. logistic regression, both logged to MLflow) | Current champion: gradient boosting (AUC 0.82 vs 0.76) because supply shortfall × yield gap × lead-time interactions are non-linear. Per-launch SHAP contributions make it explainable to an NPI steering committee. | GBM is less transparent than coefficients; SHAP drivers are shown on every launch. On a different data vintage the simpler model can win (it did on an earlier iteration), so selection is data-driven, not hard-coded. |
| 5 | **Two-stage model: predict yield first, then risk at predicted yield** | Pilot-to-line yield gap is the hidden multiplier. The same material plan covers 92% of need at pilot yield but only 72% at production yield. Making it explicit turns into an engineering action (yield sprint). | Errors compound across two models. Mitigated by blending in production-trial evidence as soon as MES has it. |
| 6 | **One feature module for training, scoring, the agent's what-if tool and the app** (`src/npi/features.py`) | No train/serve skew. The advisor's simulation produces exactly the score the next scoring job will publish. | The agent package carries the feature code and model artifacts, so it is re-logged when models change (automated in notebook 08). |
| 7 | **Mitigations are modeled as feature effects** (playbook `effect_json`) rather than a separate optimizer | Simple, auditable, explainable ("dual-source expedite pulls PPAP in 6 weeks"). It lets the same risk model quantify any action combination. | Effects are planning assumptions, not learned causal effects. They are documented and editable in the playbook table. With enough history the next step is learning effects from post-mortems. |
| 8 | **Ramp-peak window = SOP + 8 weeks** for "qualified capacity" | Physical reality: ramp demand peaks about 6-10 weeks after SOP. A second source that qualifies at SOP+4 still protects the peak. The risk score and the supply curve use the same definition. | A single global window. Per-program ramp shapes could refine it. |
| 9 | **Lakebase synced tables for reads, native Postgres for writes, Lakehouse Sync back to UC** | Millisecond app reads. Transactional writes with constraints. Decisions land in the lakehouse as CDC history, so analytics, Genie and the model see them. One governed loop. | Triggered (not continuous) sync keeps cost down. Freshness is minutes, which is right for weekly launch reviews. |
| 10 | **Event-driven re-score** (job table-update trigger on the Lakehouse Sync table) instead of a scheduled loop or in-app scoring | The model runs where the governed data and UC models are. Fires only when something changes. | A few minutes of latency instead of instant. The app shows the advisor's simulated result immediately, so users don't wait. |
| 11 | **Batch GenAI briefs with `ai_query` (GPT-5.5)**; **interactive agent with Claude Sonnet 5.5** | Briefs need strict JSON-schema output for the app and a quality gate. FMAPI Claude endpoints reject the forced tool use that JSON-schema translation needs, so GPT handles batch. The interactive advisor needs strong multi-step tool use, where Claude excels. | Two model vendors to govern. Both are served through Databricks FMAPI under the same AI governance. |
| 12 | **The agent never commits actions; a human approves in the app** | Supply commitments carry cost and supplier relationships. Human-in-the-loop is non-negotiable for a steering committee. The eval set has a probe that the agent refuses to "approve" on its own. | One extra click. |
| 13 | **On-behalf-of-user auth for the agent and Genie** | The agent's tool calls run with the caller's UC permissions, so ABAC masks and regional row filters apply to AI answers too. Automatic passthrough also failed against the schema's ABAC policies, and creating a new service principal needed approval. | Users need warehouse CAN_USE. The app requests `sql`, `dashboards.genie` and `serving.serving-endpoints` scopes. |
| 14 | **Persona entitlements table for ABAC** (not groups) | Instant, auditable persona toggle for the demo. In production it maps to IdP groups. Workspace-local group membership is not visible to `is_account_group_member` and is cached. | Must be kept in sync with the IdP; a sync job would handle that in production. |
| 15 | **Reused two generic governed tags** (`masking_rule`, `rls_filter_key`) | The shared demo account had hit its governed-tag quota. Policies are scoped to this schema only. | At Altura we would create `btd_data_class` / `btd_region_scope`. |
| 16 | **Synthetic data with an engineered hero launch** | No customer data may be used. The hero (AFT-7200) makes the story concrete. The other 455 launches are generated with a documented causal outcome model. | Absolute numbers are illustrative. The value model states its assumptions and is parameterized for Altura's real figures. |
| 17 | **Schema/catalog: dedicated schema in the workspace catalog** | No metastore CREATE CATALOG for the main data. A short-lived FEVM grant was used only to register Lakebase as a UC catalog. | The catalog name is generic. It is a bundle variable, so moving to e.g. `btd_supply_chain` is one setting. |
| 18 | **Everything as code**: DAB bundle (pipeline + jobs), app bundle, notebooks executed locally via Databricks Connect so outputs are committed | Reproducible, reviewable, and the repo carries text execution evidence. | Two bundles (data platform + app) to deploy. |
| 19 | **Release gate on the packaged agent, not only the in-process one** (notebook 08 reloads the logged model the way Model Serving does, runs the what-if, and refuses to deploy on failure) | Browser testing of the deployed app found the served what-if failing while the evaluation passed: two `models:/` artifacts were packaged to the same path, so the risk model overwrote the yield model. The evaluation ran the agent in-process, where it loads `@champion` directly. | One extra cell and about a minute per release. The gate also checks the served endpoint after rollout. |
| 20 | **Altura light theme by default, with a user-selectable dark mode** (stored per browser; class-based tokens that keep Altura red and the risk colors) | Client-facing consistency: the demo looks the same on every presenter's laptop regardless of OS setting, while users who prefer dark can switch. Chart colors are converted from oklch to rgb because ECharts cannot derive hover colors from oklch (bars vanished on hover). | Two palettes to keep in sync; status tones are semantic classes so both themes keep AA contrast. |
